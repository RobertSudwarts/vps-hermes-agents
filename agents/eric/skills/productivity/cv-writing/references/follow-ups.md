# Lean CV follow-ups

Identify the existing application, current saved draft and exact requested change from context. Recover only missing state after context loss. A file list does not require reading every file; a local edit does not require fresh vacancy research or the full career history.

## Sentence, skills row or section edit

1. Read the affected passage and capture its pre-edit text for comparison. Preserve accepted wording elsewhere. If the request changes a fact, retrieve only the relevant evidence; use the substantive method only when the hiring argument genuinely changes.
2. Apply the exact scoped change to `working/cv.md`. Removing a tool from one skills row does not remove supported experience references. Omitting a role applies to this application, not the career record or future applications.
3. Rob's explicit request to add a tool confirms listing it, not proficiency, years, scale or project attribution. Save new confirmations with provenance in existing evidence notes, without changing protected sources. Carry confirmed corrections into the affected draft unless he asks to hold them.
4. Check a deterministic before/after diff: only authorised passages changed. Show only the revised passage unless a full draft was requested. Do not regenerate documents or change frozen revisions.

When positioning misses the mark, revise the affected paragraph/section rather than cycling through labels or full-document versions. Formatting questions or inspection requests do not authorise an edit or rebuild.

## PDF handoff

Identify the exact latest saved Markdown, including accepted edits. Confirm Rob explicitly approved that version and explicitly requested a PDF; approval of an earlier version does not cover subsequent edits. Reuse clear approval already in context rather than asking again. If either condition is missing, obtain only the missing decision; never substitute internal review.

Hand off to `career-pdf` to freeze the approved text. Do not build here or silently rewrite content during production. Content changes return to Markdown review; typography/template issues remain production concerns requiring separately scoped handling, not CV edits. Preserve existing revisions and submitted artifacts.

Form-answer follow-ups use [form answers](application-form-answers.md); submission reports use [application records](application-records.md). Neither route requires a CV rewrite. Use existing notes and tools, compact diffs and targeted reads; do not add infrastructure to demonstrate efficiency.
